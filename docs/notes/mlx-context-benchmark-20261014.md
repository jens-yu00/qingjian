# MLX 同音词首选测速（2026-10-14）

目的：依据社区实测选择本机框架，再用本机数据判断大模型能否承担首选决策。设计见 [大模型首选](../design/llm-first-homophones.md)，复现入口见 [测量工具](../../tools/context-bench/README.md)。本轮不修改已安装青简或其个人数据。

## 社区证据筛选

- [oMLX 同配置提交](https://omlx.ai/benchmarks/performance/q7p0z1gm)：M1 Pro、16 GPU 核、32 GB，Qwen3.5-4B **8-bit**；1K 上下文 PP 271.2 tok/s、TG 33.5 tok/s、峰值 5.9 GB。它支持在本机优先尝试 MLX，但不当作本次 4-bit 首选延迟。
- [M3 Ultra 单机对照](https://terminalbytes.com/ollama-vs-llama-cpp-vs-mlx-mac-2026/)：2026-09-20，Qwen3.5-9B，原生 mlx-lm 107.5 tok/s、llama-bench Q4_K_M 77.8 tok/s。作者给出版本、量化与命令，属于同机部署方案比较；量化格式和生成长度不同，不把约 38% 的差值外推成本机提升或能耗节省比例。
- [M4 的可复现 MLX 4B 测试](https://github.com/AayanHidol/qwen-m4-benchmark)：提供脚本和原始结果，4-bit TTFT 中位数 262.2 ms。用于支持短请求路线，不挪用为 M1 Pro 的成绩。

采纳结论：本机以 MLX 为首选。无原始条件的口头速度倍数，以及未测量的省电百分比不进入设计依据。输入法主要看短请求的完整决策耗时，而非长篇续写的 TG。

## 本机协议

- Apple M1 Pro，10 CPU 核、16 GPU 核、32 GB；macOS 26.7.1；接交流电，电池 80%、未充电。未关闭用户其他应用，也未修改低电量模式。
- 独立 `uv` Python 3.12.11 环境，mlx-lm 0.32.0、mlx 0.32.3；完整依赖记录在 [固定结果目录](../../tools/context-bench/results/20261014/)。
- 模型 `mlx-community/Qwen3.5-4B-4bit`，revision `0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`；权重 3,034,300,695 字节，SHA256 `5fb9acd0246866381cf8c5c354c6db1019f6498eec4ccb4f5edcc71ffeacb2db`。
- 16 个公开合成语境。先用当前引擎、随包小模型和产品词库导出完整同音候选，4B 使用同一候选集合（3–12 项）；无个人数据，候选位置轮换三次。
- 关闭思考，一次前向计算读取合法单 token 标签的相对分数，不生成解释和完整 JSON。包含分词、缓存复制、GPU 同步与分数读取，不含 HTTP、输入法防抖、窗口绘制。
- 前缀缓存验证逐 token 相同，只保存固定指令或已知上文；上文预处理成本单列。结果不能复用。MLX 分配器缓存上限 256 MiB。
- 额外模拟“旧首选有最高个人偏好”的冲突，给旧首选相对 2 倍的分数修正；这是合成压力检查，不是实测用户词频融合，也不是校准后的正确概率。

## 现有小模型对照

原始证据 [homophone-baseline.json](../../tools/context-bench/results/20261014/homophone-baseline.json)。16 项首选命中 14 项；两个错误为“通往山顶的小路长满了 + jingji → 经济（期望荆棘）”和“为了让群成员都能看到，请把这条消息 + zhiding → 制定（期望置顶）”。

这组用例只说明具体行为差异，不能外推日常选词准确率。

## 4B 本机结果

| 热态路径 | 样本次数 | P50 | P95 | 最大值 |
|---|---:|---:|---:|---:|
| 标签选择，每次完整提示词 | 48 | 429 ms | 528 ms | 529 ms |
| 标签选择，固定指令前缀缓存 | 48 | 321 ms | 329 ms | 451 ms |
| 标签选择，当前上文也已预处理 | 48 | 317 ms | 327 ms | 334 ms |
| 标签选择，新增 256 字背景，仅固定指令缓存 | 12 | 625 ms | 628 ms | 628 ms |
| 直接输出候选词，固定指令缓存 | 48 | 244 ms | 247 ms | 248 ms |

P50 为标准中位数，P95 为 nearest-rank。原始逐项时间完整保存，报告聚合字段从原始行计算。

- 进程内模型加载 1.86 秒，紧接的第一次标签请求 2.44 秒；这是新进程启动测量，不是重启机器后的冷磁盘测量。
- 固定系统前缀准备 186 ms；每个短上文的完整前缀预处理耗时中位数 187 ms、最大 191 ms。短上文缓存只节省约 4 ms 的中位数，不能为了宣传快而隐去预处理成本。
- 标签测量含长语境后的 MLX 峰值分配 3.06 GB；直接输出词的独立进程为 2.66 GB。标签进程峰值 RSS 1.91 GB；这些是不同观测口径，不相加、不把 RSS 当作统一内存总占用。
- 直接输出词的请求同时减少了候选格式长度，并改用 `mlx_lm.stream_generate`；完整计时含结束符。两条路径并非只有“字母还是词”这一个变量，不能据此断言生成一定比打分更快。
- 本轮未运行 HTTP 服务，没有把防抖或 IMK 绘制算入模型时延。已结束测量进程，没有让 4B 常驻后台。

## 准确率与不采用的原因

三个标签模式在同一轮换上给出相同选择，均为 **45/48 精确命中**；模拟旧首选 2 倍个人偏好后 **46/48**。三次轮换是同一语境的敏感性检查，不是 48 条独立测试语境。

标签选择的误差：

- “荆棘”“置顶”两例，在三种候选位置下均改对。
- “炒菜时只需要加入少量 + shiyan”，食盐排到后面后，分别选成“实验”和“试验”。2 倍个人偏好也无法救回。这是明确错误。
- “项目启动前，团队需要先 + zhiding”有一轮选择“制订”，预设答案是“制定”。二者在这个片段中均合理，因此 **语义可接受为 46/48**，不能把这一项和“食盐→实验”混为一谈。施加偏好后恢复了“制定”。

直接输出词的独立对照仍为 **45/48**，输出全部属于合法候选；“食盐”两轮选成“实验”，另有“尊重客观 + shishi”一轮从“事实”错成“实施”。因此不能把错误归因于字母编号这一因素，也不能以合法输出率 100% 宣称选词可靠。

**决定：4B 速度可以继续作为参照，但准确性不足以接管首选。** 用户明确准确率优先，并要求停止 9B 下载；已终止下载并清理本轮未完成文件，未测试 9B。下一方向见 [决策模型项目筛选](decision-models-20261014.md)。不修改当前输入法配置、不安装替换版本、不消耗云 API。
