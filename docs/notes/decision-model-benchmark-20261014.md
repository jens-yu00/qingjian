# 专用决策模型的中文同音词实测（2026-10-14）

结论：专用决策模型在本轮中文同音词样例中有明确净收益。按准确率优先，下一轮以 Nox 4B 为主测对象，Sol 2B 为速度对照；本轮不接管输入法首选。

本轮只运行本机专用分类决策头，没有通用 LLM 文本生成或云 API 调用。已安装输入法保持用户确认通过的 `015c9ad` 版本。

## 方法与边界

- 本机 Apple M1 Pro、32 GiB 内存、macOS 26.7.1；Python 3.12.11，MLX/MLX-LM 0.31.1。使用社区 MLX 转换的专用 FP32 决策头与 q4 骨干，完整校验模型包；模型、运行代码、依赖版本与数据哈希见 [原始结果](../../tools/decision-bench/results/20261014/)。
- 样例和语义复核均由助手编写，未经过独立人工盲标；保留原始标注和事后复核两种口径。108 条公开自编语境：16 条开发样例，92 条评测样例；开发与评测的拼音词族隔离。每例使用当前 Core、产品词库、bigram 与已交付小模型导出的前 12 个完整候选，不使用私人词频。标注和指令在运行前冻结，后续不根据错误修改它们。
- 原序、反序、固定种子乱序各跑一次；三次共 321 次模型请求，单候选“第一个”直接保留。这些置换不能算成 321 条独立质量样本。
- 预先标注“制定/制订”“收集/搜集”和弱语境的可接受集合；模型答题后发现“装饰/妆饰”也应列为合理变体，复核记录单独保存于 [label-review.json](../../tools/decision-bench/label-review.json)。[汉典](https://www.zdic.net/hans/%E5%A6%86%E9%A5%B0) 的“布置或打扮”释义支持该判断。复核还接纳“免费使用/免费试用”，以及宾语尚未输入时的“制定/指定”；相同复核规则同时用于基线和所有模型，不覆盖原始答案。
- 固定门槛网格只在 16 条开发样例上选择，要求三种顺序均无新增错误且有净纠正收益。该小样本仅用于筛选，不能代替已约定的 200 条开发与 1,000 条独立验收集；全局高频保护与语境个人学习尚未接入。

## Sol 2B 的实际结果

92 条评测语境中，原始标注下基线答对 75 条（81.5%）、Sol 答对 89 条（96.7%）。统一复核合理变体后，基线为 77 条（83.7%）、Sol 为 90 条（97.8%）；Sol 纠正 14 条、误改 1 条，净增加 13 条正确首选。误改率是 1/77 = 1.30%，没有达到 ≤0.5% 的验收目标；这一小样本的近似 95% Wilson 区间约为 0.23%–7.0%。

- 明确错误：“参加正式典礼时要注意礼节和仪式的 + xingshi”把原本正确的“形式”改为“行事”；三个候选顺序均出错。它是语境决策错误，不能靠候选合法性过滤掉。
- 召回失败：“程序需要访问数组里的每个元素，也就是对数组进行 + bianli”没有“遍历”候选，实际候选为“便利/变例”。这例无论模型多强都无法选对，应单独修词库/召回。
- 合理变体：“用彩灯把大厅 + zhuangshi”原序选“妆饰”，反序与乱序选“装饰”；“他刚刚提到了自己的 + jingli”在精力/经理间变化，都在预设可接受集合。它们提示需要接入已约定的近似平局裁决，不能把极小分差当成充分的改首选证据。
- 开发集选出的最小有效 logit 差门槛为 0；因此这次挑战者统计等于模型直接选择。没有用评测集的“行事”错误反调门槛，再把同一组数据宣布成独立验收通过。

热态 320 次请求：P50 227 ms，P95 325 ms；加载和校验约 8.06 s，首次请求 1.37 s。MLX 峰值 1.92 GB，进程峰值 RSS 1.43 GB。两种内存口径不能相加。时延包含分词与完整决策，不含输入法防抖和候选绘制；未把这些数值换算成耗电百分比。

| 上文 + 拼音 | 基线 | Sol |
|---|---|---|
| 把剩菜放进冰箱可以延长食物的 + baoxian | 保险 | 保鲜 |
| 这个方案不能只停留在纸上，还需要亲自 + shijian | 时间 | 实践 |
| 拍照时请保持身体 + jingzhi | 精致 | 静止 |
| 收到求助后，救援队立即作出 + xiangying | 相应 | 响应 |

## Nox 4B 对照与最终取舍

同一固定版本的 [MLX 转换](https://huggingface.co/jbilcke/vllm-decision-2.0-mlx) 提供了 [Nox 4B 专用决策头](https://huggingface.co/vllm-sr/Decision-2.0-Nox-4B)。两款分别运行，每款 321 次请求；没有同时驻留两款模型。

下面均为 92 条评测语境、原候选顺序、统一语义复核口径。误改是原本正确而被改错，不能用总正确率代替：

| 路径 | 正确 | 纠正 / 误改 / 净收益 | 热态 P50 / P95 | MLX 峰值 |
|---|---:|---:|---:|---:|
| 当前基线 | 77/92（83.7%） | — | — | — |
| Sol 2B 直接选择 | 90/92（97.8%） | 14 / 1 / +13 | 227 / 325 ms | 1.92 GB |
| Nox 4B 直接选择 | 91/92（98.9%） | 14 / 0 / +14 | 572 / 836 ms | 3.66 GB |
| Sol 开发集门槛 0 | 90/92（97.8%） | 14 / 1 / +13 | 同上 | 同上 |
| Nox 开发集门槛 1 | 90/92（97.8%） | 13 / 0 / +13 | 同上 | 同上 |

Nox 原始标注也是 91/92；其目标在候选池中的 91 条原序样例全对。它保住了 Sol 误改的“形式”，但不能据此说完全不受候选顺序影响：反序会把“这次只是彩排，明晚才是 + zhengshi”的“正式”改成“正事”（差值约 0.19）。开发集反序/乱序也出现“事实→实施”的误改，促使只用开发集选出的门槛升到 1。

该门槛应用于三种评测顺序，分别得到 90/92、91/92、91/92，均无误改；原序因此少改正一条“位置→未知”。这是真实取舍：减少误改也可能放弃本来能改对的机会。Sol 三种顺序在统一复核后均为 90/92、纠正 14、误改 1。置换不重复计算为独立语境。

Nox 加载及校验约 3.87 s、首次请求 1.08 s；进程峰值 RSS 2.48 GB。两款冷启动只各测一次，文件缓存状态不同，不用来断言 4B 启动更快。Nox 热态约为 Sol 的 2.5 倍，P95 已超过原先 600 ms 的体验目标，尚未加输入法防抖/绘制；不能直接当成已经解决产品延迟。

**推进决定：以 Nox 4B 做下一轮准确率验证主模型，保留 Sol 2B 的速度对照。** 原因是当前证据中 Nox 的直接选词更准，校准门槛后的三种顺序都保住了原本正确的首选，符合用户准确率优先的取舍。其优势只有少量样例，还不构成全面胜出的证明。下一轮扩大校准集和独立验收集，测试真实输入节奏下有效返回的比例，再决定本地 4B 是否值得长期驻留、是否需要云端专用决策服务对照。

本轮 Nox 门槛后的误改为 0/77，但近似 95% Wilson 上界仍为 4.75%；不能宣布已验证误改率 ≤0.5%。也未实现全局高频分层门槛、个人平局学习或撤销负反馈。它们需要与最终策略一起回放验收。
